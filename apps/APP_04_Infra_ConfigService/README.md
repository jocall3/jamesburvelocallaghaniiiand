# APP_04_Infra_ConfigService

**Service for managing dynamic application configuration and feature flags, allowing for runtime changes without redeployment.**

---

## Disclaimer

This service is a core infrastructure component. Misconfiguration can lead to widespread outages across the entire application ecosystem. All changes, especially in production environments, should be subject to rigorous review and approval processes. This system provides tools for control but does not replace sound operational judgment. Use with caution.

---

## 1. Problem Statement

In a large, distributed ecosystem of 75+ applications, managing configuration is a critical challenge. Static configuration files (`config.yaml`, `.env`) are brittle, require a full redeployment for minor changes, and make it impossible to perform sophisticated operational maneuvers like gradual feature rollouts, A/B testing, or emergency kill-switching.

`APP_04_Infra_ConfigService` solves this by providing a centralized, dynamic, and versioned configuration store. It acts as the central nervous system for controlling the behavior of the entire application suite, enabling operators to:

*   **Change application behavior in real-time** without redeploying services.
*   **Manage feature flags** to decouple deployment from release.
*   **Segment configurations** by environment, region, user cohort, or any other dimension.
*   **Maintain a complete audit trail** of every configuration change.
*   **Enable emergency kill-switches** for risky features or integrations.

This service is fundamental to achieving operational agility and resilience at scale.

## 2. Architecture

The architecture is designed to balance the tension between **Centralized Control** and **Decoupled Execution**. It provides a single source of truth for configuration while ensuring that client applications remain resilient even if the service is temporarily unavailable.

### Core Tension: Centralized Control vs. Decoupled Execution

*   **Centralized Control**: A single API and UI to manage the behavior of the entire ecosystem. This is powerful for governance, security, and operational consistency. An operator can disable a faulty AI provider integration across all 75 apps with a single change.
*   **Decoupled Execution**: Each of the 75 apps must operate independently. They cannot have a hard dependency on the config service being available 100% of the time. This tension is architecturally resolved through mandatory client-side caching, fallback mechanisms, and a "fail-static" design principle embedded in the Core SDK. The system is designed for high availability, but clients are designed for graceful degradation in its absence.

### Key Components:

1.  **API Layer**: A high-throughput gRPC and REST API for fetching and modifying configurations. All access is authenticated and authorized via the shared identity model.
2.  **Logic Layer**: Handles the core business logic, including schema validation for configs, versioning of every change, and a powerful segmentation engine for targeting rules.
3.  **Caching Layer**: An aggressive Redis cache stores frequently accessed configurations to ensure low-latency reads for client applications.
4.  **Persistent Storage**: A PostgreSQL database stores the canonical, versioned history of all configurations and audit logs. This provides durability and the ability to roll back to any point in time.
5.  **Event Bus**: Integrates with the shared NATS message bus to push configuration updates to clients in real-time, eliminating the need for constant polling.
6.  **Core SDK Integration**: Client applications do not interact with the API directly. The Core SDK provides a transparent client that handles authentication, local on-disk caching (for startup resilience), real-time updates, and periodic polling as a fallback.

## 4. Cost Drivers

*   **Compute**: API server instances scale with the number of client connections and API requests. The real-time update mechanism can also be CPU-intensive at scale.
*   **Database Storage & I/O**: The PostgreSQL database stores the entire history of every configuration change. This can grow very large over time, driving storage costs and requiring provisioned IOPS for performance.
*   **Cache Memory**: Redis memory usage scales directly with the number of active configurations and segmentation rules being cached.
*   **Network Egress**: Pushing real-time updates and serving configuration data to clients across multiple regions is a primary cost driver.
*   **Message Bus Traffic**: The volume of configuration changes directly impacts the cost of the underlying NATS or Kafka infrastructure.
